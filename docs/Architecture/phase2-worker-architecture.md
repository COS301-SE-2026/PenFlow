# Phase 2 Worker Architecture

## Overview

Phase 2 extends the PenFlow architecture by introducing the active security scanning pipeline.
Unlike Phase 1, which focuses on passive OSINT only, Phase 2 does active reconnaissance and security analysis against verified target domains.

Rather than implementing one large scanning component, the pipeline is divided into a collection of independent workers, Much like the split phase 1 worker approach. Each worker is responsible for one stage of the scan and contributes information that is used by later stages.

---

# Architectural Objectives

During Phase 2 we decided to split scanning into a collection of small workers rather than one large scanner. This keeps each worker responsible for a single task while making the pipeline easier to extend in the future.

- Separate individual scanning responsibilities.
- Reduce coupling between scanning components.
- Allow workers to evolve independently.
- Standardise worker outputs.
- Simplify downstream reporting and frontend integration.
- Support future worker expansion with minimal architectural change.
- Allow the ability to do concurrent operations.

---

# Worker Responsibilities

The current Phase 2 pipeline consists of the following workers.

| Worker | Responsibility                                                                                      |
|---------|-----------------------------------------------------------------------------------------------------|
| Target Resolution | Resolve the target into IPv4 and IPv6 addresses                                                     |
| Nmap | Discover live hosts, ports and network services                                                     |
| HTTP Security | Analyse HTTP response headers and identify missing security headers                                 |
| TLS | Retrieve and analyse TLS certificates via a secure handshake                                        |
| Fingerprinting | Identify technologies running on the target                                                         |
| CPE Resolver | Convert identified technologies into standard CPE identifiers                                       |
| CVE | Search for publicly disclosed vulnerabilities  (NVD) with use of the cpe generated by other workers |

# Worker Pipeline

The current execution flow is shown below.

```
Backend API

Celery Task Queue

<>Target Resolution

<>Nmap

<>    - HTTP Security
<>    - TLS
<>    - Fingerprinting
<>    - CPE Resolver
<>    - CVE

Normalised Findings & Assets

PostgreSQL

Reporting API

Frontend UI
```

Each worker only receives the information it requires from previous stages.
Workers never communicate directly with one another. Instead, they communicate through the shared pipeline and normalised data structures that we have defined in a data contract for simplicity’s sake.

All workers conform to the same data contract and thus changes and additions are uniformly accepted rather than having to rebuild major portions of the codebase.

This is talked about more in the next section...

# Standard Worker Contract

One of the primary architectural decisions made during Phase 2 was introducing a common output structure for every worker.

Every worker returns the following structure.

```json
{
    "raw_result": {},
    "findings": [],
    "assets": [],
    "status": "completed"
}
```

Each section serves a different purpose.

| Field | Purpose |
|--------|----------|
| raw_result | Preserves the original worker output for debugging and traceability |
| findings | Stores security observations identified by the worker |
| assets | Stores infrastructure, technologies or services discovered by the worker |
| status | Indicates the worker execution state |

# Architectural Characteristics

## 1 Single Responsibility

Each worker performs one clearly defined task.
Keeping workers focused reduces complexity, improves readability and makes future maintenance significantly easier.

---

## 2 Loose Coupling

Workers do not communicate directly with one another.
Instead, information flows through the pipeline using the standard worker contract.
Reducing dependencies between workers makes it easier to update or replace individual workers without impacting the remainder of the system.
It would even be possible to remove entire workers or groups of workers without affecting the others too greatly.

---

## 3 Standardisation

Every worker produces the same output format regardless of its implementation.
This standardisation removes worker-specific logic from downstream systems and keeps the architecture consistent as additional workers are introduced.
This also allows for frontend and other backend components to be developed without the need of seeing the exact outputs per worker.

---

## 4 Separation of Concerns

Scanning, persistence, reporting and presentation remain separate architectural concerns.

- Workers are only responsible for collecting security information.
- The backend is responsible for persistence.
- The reporting layer is responsible for presenting information.
- The frontend is responsible for visualising results.

Keeping these responsibilities separated improves maintainability across the project.

---

## 5 Extensibility

The worker architecture was designed to support future expansion.
Adding another worker should only require:

- implementing the worker
- registering it within the pipeline
- producing the standard worker contract

No architectural changes should be required.

---

# Relationship to Findings and Assets

Rather than exposing raw worker output directly to the frontend, worker results are normalised into Findings and Assets.

This provides several advantages.

- consistent backend filtering
- simpler reporting
- reusable API endpoints
- worker-independent frontend components

---

# Architectural Benefits

The current worker architecture provides several quality attributes.

### Maintainability

Small workers are easier to understand, debug, modify and reproduce.

### Scalability

Independent workers can be parallelised or distributed across multiple worker processes.

### Modifiability

New scanning capabilities can be introduced without redesigning the existing architecture.

### Reusability

Normalised Findings and Assets can be reused by reporting, filtering sections in the frontend.

---

# Future Work

As additional Phase 2 capabilities are introduced, new workers should continue following the existing architectural principles.

Every worker should:

- perform one responsibility
- remain loosely coupled
- produce the standard worker contract
- integrate through the existing pipeline
